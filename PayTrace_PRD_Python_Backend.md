# PayTrace --- Product Requirements Document (PRD)

**Version:** 1.0\
**Status:** Hackathon MVP specification\
**Project:** PayPal AI Hackathon 2026\
**Product name:** PayTrace\
**Tagline:** *Don't just know a payment failed. Know exactly why.*

------------------------------------------------------------------------

## 1. Executive summary

PayTrace is an AI-powered payment investigation and observability
platform for applications that accept payments through PayPal. It
correlates PayPal orders, captures, webhooks, application events, and
customer checkout-session activity into a single payment lifecycle. An
AI investigator uses that evidence to explain likely root causes, show
supporting facts, identify related failures, estimate potential revenue
at risk, and recommend next steps.

PayTrace is not just a log viewer or a chatbot that explains an error
code. Its differentiator is **cross-signal payment investigation**: it
reconstructs what happened across the payment provider, the merchant
application, and the customer's browser session.

The project must be a genuinely working hackathon prototype. PayPal
Sandbox is the only payment environment in scope. Simulated demo events
must be visibly labelled and must never be represented as real PayPal
events.

### Elevator pitch

**AI that reconstructs PayPal payment journeys, correlates provider
events with customer-session evidence, finds likely root causes, and
recommends the next action.**

### Primary users

-   Developers integrating PayPal checkout.
-   Merchant engineering and operations teams.
-   Product/support teams investigating failed or delayed payments.
-   Platforms experimenting with AI agents that initiate payment
    actions.

### Core questions PayTrace must answer

1.  What happened to this payment?
2.  Why did it fail or become stuck?
3.  What did the customer experience?
4.  Are other payments affected by the same issue?
5.  What is the potential revenue impact?
6.  What should the operator do next, and does that action require
    approval?

## 2. Product goals and non-goals

### 2.1 Goals

-   Integrate with the real PayPal Sandbox APIs.
-   Create, approve, and capture a sandbox order through a working
    checkout.
-   Receive and verify configured PayPal webhooks.
-   Persist payment lifecycles and append-only payment events.
-   Correlate payment events with browser-session recordings where
    available.
-   Reconstruct a unified, chronological payment timeline.
-   Use AI to investigate a payment or incident from structured
    evidence.
-   Show confidence, evidence, customer impact, potential revenue
    impact, and recommendations.
-   Detect basic failure spikes using deterministic rules.
-   Support safe operator-approved money actions, especially refunds.
-   Provide a polished dashboard and reliable three-minute demo path.
-   Publish a public repository with setup instructions, `.env.example`,
    and a license.

### 2.2 Non-goals for the hackathon MVP

-   Live-money transactions.
-   A full commercial multi-tenant SaaS platform.
-   Enterprise SSO, complex RBAC, or billing.
-   A general-purpose APM replacement.
-   Kubernetes, microservices, or a complex event-streaming platform.
-   Training or fine-tuning a model.
-   Supporting PayPal, Stripe, Razorpay, and every provider
    simultaneously.
-   Automatically accepting disputes or executing risky financial
    actions without policy checks and human approval.
-   Recording sensitive payment credentials or unnecessary personal
    information.
-   Claiming an incident or payment failure came from PayPal when it was
    generated by a simulator.

### Architecture decision

Use a **monorepo with a Next.js frontend and a separate Python FastAPI
backend**. This keeps the interface polished while making the backend
unambiguously Python. The frontend must call the FastAPI API; it must
not contain PayPal secrets or make privileged PayPal REST calls
directly.

### Important implementation notes

-   Verify the exact current Python support and available tool names in
    the PayPal Agent Toolkit before relying on a toolkit operation. If a
    required operation is not covered, use a small, tested FastAPI
    service wrapper around the official PayPal REST API.
-   Do not use Prisma in the Python backend. Use SQLAlchemy and Alembic.
-   rrweb is a browser-side JavaScript library; the Python backend
    stores and serves its events.
-   Do not add Redis or a queue unless an actual background-processing
    requirement emerges.
-   Keep the system as one frontend, one Python API, and one PostgreSQL
    database.

## 5. High-level architecture

``` mermaid
flowchart TD
    B[Customer browser / Demo checkout] --> F[Next.js frontend]
    B --> R[rrweb recorder]
    F -->|HTTPS REST| A[FastAPI Python backend]
    A --> P[PayPal Sandbox REST APIs]
    P -->|Webhook POST| W[FastAPI webhook endpoint]
    R -->|Batched session events| A
    A --> DB[(PostgreSQL)]
    A --> TL[Lifecycle and timeline engine]
    DB --> TL
    TL --> IE[Deterministic incident / evidence engine]
    IE --> AI[AI investigator]
    AI -->|Read-only evidence tools| DB
    AI -->|Recommendations / permitted tool proposals| POL[Policy and approval service]
    POL --> HITL[Human approval inbox]
    HITL -->|Approved action only| A
    A --> UI[Dashboard / Payment details / Incidents]
```

### Trust boundaries

-   Browser: public client ID only; never hold the PayPal client secret
    or AI key.
-   FastAPI: validates inputs, calls PayPal, verifies webhooks, enforces
    policies, and controls all privileged actions.
-   PostgreSQL: stores only necessary and appropriately redacted
    event/session information.
-   AI provider: receives only the minimum relevant, redacted facts
    needed for investigation.
-   Simulated events: are tagged as `source=SIMULATED` and visually
    distinguished from PayPal-sourced events.

## 7. Core user journeys

### 7.1 Real sandbox checkout

1.  User opens `/checkout`.
2.  Frontend starts a session and enables rrweb recording with privacy
    masking.
3.  User selects the demo product and clicks PayPal.
4.  Frontend requests order creation from FastAPI.
5.  FastAPI creates a PayPal Sandbox order and persists a PayTrace
    payment record.
6.  PayPal SDK handles buyer approval.
7.  Frontend asks FastAPI to capture the approved order.
8.  FastAPI calls PayPal, stores the response and updates the lifecycle.
9.  PayPal sends configured webhooks to FastAPI.
10. Webhook verification, deduplication, correlation, and status update
    run.
11. Payment detail displays the unified timeline and linked customer
    session.

### 7.2 AI payment investigation

1.  User opens a payment and clicks **Investigate with AI**.
2.  Backend gathers deterministic payment facts, timeline, webhook
    status, session metadata, and similar failures.
3.  AI receives a bounded, redacted evidence package and returns a
    validated structured response.
4.  UI shows root-cause assessment, confidence, facts, inferences,
    customer impact, potential revenue impact, and recommendations.
5.  User may ask follow-up questions that use the same server-side
    evidence tools.
6.  If evidence is insufficient, PayTrace says so rather than inventing
    a cause.

### 7.3 Incident investigation

1.  Deterministic analytics detect a threshold breach.
2.  An incident is created or updated and related payments are linked.
3.  User opens the incident, reviews affected payments and the timeline,
    and requests an AI report.
4.  AI summarizes evidence and recommends next steps; it does not
    manufacture unobserved events or claim potential revenue is actual
    loss.

### 7.4 Human-approved refund

1.  AI or an operator proposes a refund.
2.  Policy engine checks the amount and action type.
3.  If approval is required, create a pending approval ticket.
4.  A human approves or denies the ticket.
5.  Only the backend approval handler can invoke the PayPal refund
    operation.
6.  Persist the decision, actor, PayPal response, and resulting
    lifecycle events.

## 8. PayPal integration requirements

### 8.1 Environment

Use the PayPal Developer Dashboard to create a Sandbox app and test
buyer account. Never use live credentials or live-money transactions for
the hackathon demo.

### 8.2 Python PayPal service

Create `backend/app/services/paypal/` with: - OAuth access-token
acquisition and safe token reuse. - Create order. - Get order. - Capture
approved order. - Retrieve capture/order details as needed. - Refund
capture, only through policy-checked backend code. - Webhook signature
verification. - Consistent error mapping and safe structured logging. -
Request timeouts and clear handling for network errors. - Correlation
metadata for every outbound call. - Optional transaction search if
required and supported for the selected account/API.

Use the official PayPal REST API and current documentation for exact
endpoints, request bodies, event names, and verification behavior. Do
not guess API fields or assume every webhook is delivered for every
checkout.

### 8.3 Checkout

-   Use the PayPal JavaScript SDK with the public client ID.
-   Use the Python backend for order creation and capture.
-   Display the PayPal order ID and PayTrace payment ID in the
    successful demo.
-   Prevent accidental duplicate order/capture actions.
-   Treat network timeouts as an **unknown outcome** until the
    order/capture state is reconciled; do not blindly repeat a
    money-moving request.

### 8.4 Webhook endpoint

Required route: `POST /api/webhooks/paypal`

Responsibilities: 1. Receive PayPal webhook request. 2. Verify its
signature using the configured webhook ID and PayPal verification
mechanism. 3. Reject invalid requests safely. 4. Store a minimally
necessary, redacted payload and delivery metadata. 5. Deduplicate by
PayPal webhook event ID. 6. Correlate by order ID, capture ID, or
another supported PayPal resource identifier. 7. Attach the event to the
correct lifecycle; preserve unmatched events for later reconciliation
instead of silently dropping them. 8. Update lifecycle state only
according to verified event semantics. 9. Trigger incident evaluation
where appropriate. 10. Return a successful response promptly after safe
durable acceptance; do longer work asynchronously only if the
architecture supports it reliably.

Webhook handling must be idempotent. PayPal can retry deliveries, and
event arrival order must not be assumed.

### 8.5 Minimum webhook coverage

Subscribe to the supported Sandbox events relevant to the implemented
flow, including where available: - `CHECKOUT.ORDER.APPROVED` -
`PAYMENT.CAPTURE.PENDING` - `PAYMENT.CAPTURE.COMPLETED` -
`PAYMENT.CAPTURE.DENIED` - `PAYMENT.CAPTURE.REFUNDED` - Relevant
dispute-created/resolved events if the dispute view is implemented.

Treat this list as a starting point, not a guarantee that all events
occur in each test. Confirm exact current event names and payload shapes
in PayPal's documentation and the Developer Dashboard.

### 8.6 PayPal Agent Toolkit

Use the PayPal Agent Toolkit Python integration for agentic PayPal
operations only after validating its current Python support and exact
tool catalog. Minimum target: - Create/get/pay order, if supported by
the current Python toolkit. - List/get transaction or dispute
information where supported. - Refund behind a server-enforced
human-approval policy.

If toolkit support does not cover a required operation, implement a
small official REST API wrapper. The user interface and AI must not
depend on a fabricated tool response.

## 9. Data model

Use SQLAlchemy models and Alembic migrations. Store money as
fixed-precision decimal values or integer minor units; never use binary
floating-point as the source of truth for amounts.

### 9.1 `Payment`

Minimum fields: - `id` --- internal UUID or stable ID. -
`paypal_order_id` --- nullable until created; unique when present. -
`paypal_capture_id` --- nullable. - `customer_ref` --- pseudonymous
identifier; avoid unnecessary PII. - `session_id` --- nullable session
reference. - `amount`, `currency`. - `status` --- internal normalized
lifecycle status. - `failure_code`, `failure_reason` --- nullable,
sanitized. - `actor` --- `human`, `agent`, or `demo`. - `source_mode`
--- `PAYPAL_SANDBOX` or `SIMULATED`. - `created_at`, `updated_at`.

### 9.2 `PaymentEvent`

Append-only event record: - `id`, `payment_id`. - `event_type`,
`source`, `status`. - `occurred_at`, `received_at`. - `latency_ms` ---
nullable. - `paypal_order_id`, `paypal_capture_id` --- nullable
correlation fields. - `metadata_redacted` --- JSON. - `trace_id` /
`span_id` --- nullable. - `is_simulated` --- boolean.

### 9.3 `PayPalWebhook`

-   `id`.
-   `webhook_event_id` --- unique idempotency key.
-   `event_type`, `resource_type`.
-   `payment_id` --- nullable until correlated.
-   `payload_redacted` --- JSON.
-   `received_at`, `processed_at`.
-   `processing_status`, `processing_error` --- sanitized.
-   `signature_verified` --- boolean.

### 9.4 `Session`

-   `id`, `visitor_ref`.
-   `payment_id` --- nullable until correlated.
-   `started_at`, `ended_at`.
-   `user_agent` --- minimize or redact where practical.
-   `metadata_redacted` --- JSON.
-   `recording_enabled` --- boolean.

### 9.5 `SessionEvent`

-   `id`, `session_id`, `occurred_at`.
-   `event_type`.
-   `payload_redacted` --- JSON or suitable compressed representation.
-   Add batching/size limits to avoid excessive database writes.

### 9.6 `Incident`

-   `id`, `title`, `severity`, `status`.
-   `started_at`, `ended_at`.
-   `affected_payment_count`.
-   `revenue_at_risk`, `currency`.
-   `root_cause`, `confidence`, `ai_summary` --- nullable until
    investigated.
-   `created_at`, `updated_at`.

### 9.7 `AIInvestigation`

-   `id`, `payment_id` nullable, `incident_id` nullable.
-   `question`.
-   `root_cause`, `confidence`, `severity`.
-   `evidence` --- structured JSON.
-   `customer_impact`, `business_impact`, `recommendation`.
-   `model_name`, `created_at`.
-   Do not store hidden chain-of-thought. Store concise explanations and
    evidence instead.

### 9.8 `ApprovalTicket`

-   `id`, `payment_id`, `action_type`, `amount` nullable.
-   `reason`, `status` (`PENDING`, `APPROVED`, `DENIED`, `EXECUTED`,
    `FAILED`).
-   `requested_by`, `decided_by`, `decided_at`.
-   `paypal_result_redacted`, timestamps.

### 9.9 Constraints and indexes

-   Unique index on `paypal_order_id` when non-null.
-   Unique index on `webhook_event_id`.
-   Index payment events by `(payment_id, occurred_at)`.
-   Index payments by `(status, created_at)`.
-   Index incidents by `(status, severity, started_at)`.
-   Use foreign keys and database transactions for lifecycle updates.
-   Keep raw secrets and full unredacted customer-session payloads out
    of storage.

## 10. Lifecycle and timeline engine

### 10.1 Normalized lifecycle states

Use a controlled state model such as:

``` text
CREATED
  -> APPROVED
  -> AUTHORIZED (if authorization flow is used)
  -> CAPTURE_PENDING
  -> CAPTURED
  -> REFUND_PENDING
  -> REFUNDED

Possible terminal/exception states:
CAPTURE_FAILED, DENIED, VOIDED, EXPIRED, DISPUTED, DISPUTE_RESOLVED, UNKNOWN
```

Do not force every payment through every state. Store the provider's
original event/status alongside the normalized state.

### 10.2 Timeline event sources

-   PayTrace frontend/application events.
-   PayPal API request/response summaries.
-   Verified PayPal webhook events.
-   Payment state transitions.
-   rrweb session markers/metadata.
-   Policy decisions and human approval actions.
-   Clearly labelled simulated events.

### 10.3 Timeline requirements

Every timeline item should include: - Timestamp and source. - Event type
and readable label. - Status/severity. - Relevant payment/provider
IDs. - Safe metadata. - Real versus simulated marker. - Latency when
measured.

Sort by event occurrence time, but retain receipt time for delayed
webhooks. Handle out-of-order events without incorrectly regressing a
final payment state. Never delete an event just because it is
duplicated; preserve delivery metadata as needed while deduplicating
logical processing.

### 10.4 Incident rules

Start with deterministic rules, not a trained ML model: - A capture
remains pending or authorized beyond a configurable threshold. -
Capture-denied rate crosses a threshold in a time window. - Overall
payment failure rate rises above baseline. - Webhook delay exceeds a
threshold. - Duplicate webhook deliveries or suspicious repeated capture
attempts are detected. - Similar failure codes spike across multiple
payments.

Thresholds must be configurable. Keep the detection explanation visible
so users understand why an incident fired.

## 11. AI Payment Investigator

### 11.1 Design principles

-   AI is an investigator, not a generic chat wrapper.
-   Compute facts and metrics deterministically before invoking the
    model.
-   Use server-side read tools to retrieve actual records.
-   Provide only relevant, redacted evidence.
-   Separate **FACT**, **INFERENCE**, and **RECOMMENDATION** in output.
-   Do not expose hidden chain-of-thought.
-   If evidence is missing or contradictory, say **Insufficient
    evidence** or explain the uncertainty.
-   AI-generated root cause is not itself a provider fact.
-   AI may propose a money action, but the backend policy layer---not
    the model---authorizes execution.

### 11.2 Investigation tools

Implement backend functions such as: - `get_payment(payment_id)` -
`get_payment_timeline(payment_id)` - `get_paypal_events(payment_id)` -
`get_session_summary(payment_id)` -
`get_session_events_around_failure(payment_id)` -
`find_similar_failures(payment_id)` -
`compare_with_successful_payment(payment_id)` -
`get_incident_stats(time_window)` -
`get_failure_statistics(time_window)` -
`calculate_revenue_at_risk(filters)`

Validate IDs and arguments; never allow the model to run arbitrary SQL
or arbitrary URLs.

### 11.3 Deterministic facts to prepare

-   Was order creation successful?
-   Was buyer approval recorded?
-   Was capture requested?
-   Did the capture API return success, denial, or an unknown outcome?
-   Which verified PayPal events arrived and when?
-   Did webhook delivery lag or fail verification?
-   Were duplicate attempts detected?
-   What was the end-to-end and stage-level latency?
-   Were similar failures observed in the same time window?
-   What did the customer browser session show immediately before the
    failure, if recording is enabled?
-   How many payments and what transaction value are affected?

### 11.4 Structured AI response

Validate model output with Pydantic. Example shape:

``` json
{
  "root_cause": "Capture status is unresolved after the backend timed out.",
  "confidence": 0.78,
  "severity": "HIGH",
  "facts": [
    "Order approval was recorded.",
    "The capture request timed out in the merchant backend.",
    "No verified capture-completed webhook has been received yet."
  ],
  "inferences": [
    "The final payment outcome is not yet established."
  ],
  "customer_impact": "The checkout may appear incomplete to the customer.",
  "business_impact": "Potential revenue impact; do not count this as a confirmed loss.",
  "recommendation": "Reconcile the order/capture state with PayPal before attempting another capture.",
  "evidence_event_ids": ["event-id-1", "event-id-2"],
  "is_incident_likely": false,
  "insufficient_evidence": false
}
```

The example is illustrative, not a predetermined diagnosis. The AI must
generate its response from the records actually retrieved.

### 11.5 Fallback behavior

If the AI provider is unavailable: - Continue to show deterministic
payment facts and timeline. - Show a clear message that AI investigation
is temporarily unavailable. - Optionally show a rule-based diagnostic
summary clearly labelled as deterministic. - Never fabricate a
successful AI investigation.

## 12. rrweb session recording and replay

### 12.1 Frontend

Use `@rrweb/record` on the demo checkout and `@rrweb/replay` for replay.
Generate a session ID and associate it with the payment after order
creation or capture.

### 12.2 Backend

-   Accept session-event batches through a validated API.
-   Enforce payload size and event-count limits.
-   Persist events efficiently.
-   Return events for a session or bounded time window.
-   Correlate a replay with payment and timeline markers.

### 12.3 Privacy requirements

-   Mask input values and sensitive elements by default.
-   Never record passwords, PayPal credentials, card details, secrets,
    or payment form values.
-   Do not attempt to capture PayPal-hosted checkout internals that are
    inaccessible or inappropriate to record.
-   Avoid unnecessary PII. Provide a clear demo notice that browser
    interaction recording is enabled.
-   Sanitize payloads server-side as well as in the browser.
-   Set retention/size limits for demo recordings.
-   If session recording is blocked or fails, payment processing must
    still work.

### 12.4 Replay experience

-   Button: **Replay customer session**.
-   Optional button: **Replay around failure**, showing a bounded window
    (for example, five seconds before and after a failure marker).
-   Display the event timeline alongside the replay.
-   Show a clear empty state when no recording is available.
-   Never imply rrweb captures the full contents of PayPal-hosted pages

## 17. Security, safety, and reliability

### 17.1 Secrets

-   Keep all secrets in environment variables or the deployment secret
    manager.
-   Never commit `.env`.
-   Never expose `PAYPAL_CLIENT_SECRET`, AI API keys, or database
    credentials to the frontend.
-   Keep `.env.example` free of real credentials.

### 17.2 Payment safety

-   Sandbox only.
-   Never blindly retry an operation with an unknown outcome.
-   Reconcile order/capture status before retrying after a timeout.
-   Use idempotency support where the selected PayPal API operation
    supports it; do not assume every operation accepts the same
    idempotency mechanism.
-   All refunds must pass server-side policy checks.
-   Refunds above a configurable threshold require explicit human
    approval.
-   Dispute acceptance, if implemented, must always require human
    approval.
-   The model cannot bypass the policy service by calling the PayPal API
    directly.
-   Log who proposed, approved, denied, and executed each action.

### 17.3 Webhook safety

-   Verify webhook signatures.
-   Deduplicate event IDs.
-   Validate payloads and correlate resource IDs carefully.
-   Do not trust browser-submitted provider statuses.
-   Handle retries and out-of-order delivery.
-   Avoid long-running AI calls before acknowledging a verified webhook.

### 17.4 Data privacy

-   Redact payloads and session data.
-   Do not store card data or credentials.
-   Restrict what evidence is sent to the AI provider.
-   Avoid putting unnecessary PII in logs or AI prompts.
-   Apply event payload size limits and session-retention limits.

### 17.5 App reliability

-   Return understandable errors if PayPal, the AI provider, or
    PostgreSQL is unavailable.
-   If AI fails, preserve deterministic diagnosis and payment history.
-   A session-recording failure must not break checkout.
-   Add rate limits to AI endpoints where practical.
-   Use transactions for multi-table lifecycle updates.
-   Add request IDs and structured logs for debugging.

## 26. Final product principle

PayTrace should make the following chain visible and trustworthy:

**Payment attempt → PayPal API facts → verified webhook events →
application lifecycle → customer-session evidence → deterministic
analysis → AI explanation → safe next action.**

The strongest hackathon submission is not the one with the most screens
or the most APIs. It is the one that demonstrates this complete chain
with a real Sandbox payment, an understandable investigation, honest
evidence boundaries, and a safe human-approved action.
